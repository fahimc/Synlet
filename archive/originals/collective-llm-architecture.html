Build this first

A small TypeScript harness manages the task lifecycle, context, permissions and model scheduling. llama.cpp serves generative GGUFs; a CPU worker serves Julia and embeddings. Ordinary tools perform exact calculation, file operations and verification.

Design choice

Do not claim this yet

This is not one trained neural network, a drop-in single GGUF, unlimited reliable context, or proven frontier-model quality. Bundling checkpoints creates one product interface—not a shared tokenizer, shared knowledge or automatically additive intelligence.

Scope boundary
Why selective? Research on scaling agent systems finds that coordination can help or hurt depending on the task. Our hypothesis is that complementary specialists plus verifiable tools will outperform indiscriminate agent debate on local workloads. [S24]

Evidence key: Source-checked means a specification or artifact was found in the linked source—not tested locally. Planning assumption means an unmeasured estimate. Acceptance target means a proposed release gate. All untagged architecture, budgets and policies are design recommendations.

02System view

One conversation. A small, chosen team.

The controller owns the workflow. The context engine owns the working set. The host—not a model—owns permissions and execution.

Fast path

A direct answer or recognised exact calculation uses no specialist. Rules may bypass Julia when the required operation is unambiguous.

Specialist path

One expert receives a bounded context packet, returns a result, and is checked with the appropriate tool or evidence.

Composite path

The controller executes a short dependency sequence: observe → calculate → patch → test. On one GPU, inference is normally sequential.

Compaction and just-in-time retrieval are established context-engineering patterns. This implementation adds explicit provenance, versioning and measurable retention gates. [S17]

1. Originals

Store content outside model memory. Keep revision, source range, project, actor and trust level. Respect retention and deletion; originals are recoverable until the user’s policy deletes them.

2. Searchable chunks

Start with 400–800-token prose chunks. Prefer functions for code, sections for documents, and related events for logs. Include neighbourhood pointers and a separate exact-identifier index.

3. Working state

Keep goal, constraints, decisions, completed work, failed attempts, unresolved issues and next action. Separate user requirements from model proposals and tool observations.

The lookup algorithm

Filter by project permissions and source version first. Union the top 20 keyword and top 20 semantic candidates; combine ranks with reciprocal-rank fusion; deduplicate; pack up to 8 relevant chunks within the token ceiling. These counts are tunable starting values. FTS5 provides keyword ranking; embeddings require a separate vector-search component. [S18] [S12]

For v0.1, use a per-project, memory-mapped vector matrix and cosine search for a bounded corpus; benchmark query latency as it grows. Move to an approximate nearest-neighbour index when measured search latency exceeds the budget. Never describe storage capacity as unlimited reliable model context.

Compaction trigger

Before each model call, count the rendered prompt with that model’s tokenizer. Above 75% of its input allowance, first remove duplicates, then compact completed work towards 55%. Keep complete tool-call/result pairs. A 3K prompt needs no artificial compression just to reach a ratio.

Qwen drafts notes; host checks IDs and preserved exact fields. On failed checks, keep original excerpts or escalate to the controller. Do not recursively summarise summaries as the only record.

Information that must survive

Current instructions and explicit corrections; numbers and units; paths and identifiers; negations; unresolved failures; proof of what actually ran. Preserve critical constraints verbatim, and never let a summary become more authoritative than its source.

The vision record links to the original image and coordinates. Text embeddings index its observations—not the raw image itself.

A valid schema or source ID does not prove that every summary sentence is true. Important factual updates require direct evidence or explicit user confirmation. Ingestion assigns IDs; models cannot create authoritative provenance.

05Execution design

A small, explicit harness—not a stack of chatbots.

Proposed foundation: Node.js/TypeScript + Fastify, a durable SQLite task machine, llama.cpp inference adapters, and a pinned Python CPU worker. No Docker is required for this design.

What we build

GatewayOne model ID, streaming replies, task status, cancel and approval endpoints.
Task machineExplicit steps, dependency state, retry budgets, checkpoints and event log.
Context engineSource ingestion, compact state, hybrid search and per-model packing.
SchedulerOne GPU generation at a time; measured memory admission and model residency.
Tool brokerPermission checks, schema checks, execution journal and output-size limits.

What we reuse

Fastify for API schema validation; llama-server for model loading and generation; SQLite FTS5 for records and keyword retrieval; Playwright for an owned, visible browser; Python for Julia, embeddings and numerical tools. [S19] [S14] [S18] [S20]

Model adapters preserve native templates and parse native tool calls into one internal format. A JSON schema constrains structure, not semantic correctness. Test each checkpoint’s parser before granting it any tool access.

Framework alternative: LangGraph already supports checkpointed workflows. Use it if the team prefers a framework to owning the state machine; do not layer both orchestration systems over each other without a specific need. [S26]

Small-model skills

Start with versioned packs: repo-fix, windows-service, browser-check, document-qa and math-check. Each pack has prerequisites, bounded steps, allowed tools, output schema and a completion test.

Expose a short skill index, then load only the selected instructions and roughly 6–10 relevant tool schemas. Keep large reference material behind lookup. Skills cannot change host permissions.

Browser and web access

Use DOM/accessibility locators first; ask the vision specialist when visual grounding is needed. After an important action, observe again. Use a separate selectable agent profile—not the ordinary live Chrome data directory. [S20] [S21]

Web search is an optional provider adapter or local index. Store source URL and fetched time. In offline mode, report the archive’s coverage and freshness; never present stored material as a fresh live search.

Tool contract, safety boundary and optional MCP integration

Each tool definition includes an input/output schema, read/write capability, allowed roots or domains, timeout, response cap, confirmation policy and retry classification. Tool outputs are stored as artifacts; models receive bounded excerpts.

tool = {
  name: "workspace.apply_patch",
  permission: "workspace_write",
  input_schema: trusted_static_schema,
  expected_revision: required,
  requires_approval: according_to_host_policy,
  retry_mode: "check_current_state_before_retry",
  response_limit_tokens: 1200
}

Optional MCP clients connect existing tool servers, but the host retains consent, scope checks and result filtering. MCP is a transport/integration boundary, not a permission grant or a security sandbox. [S22]

For compatibility, support a documented subset of chat completions: messages, basic tool schemas, streaming and a single logical model ID. Do not promise support for every client extension, logprobs or cross-model token accounting. Keep exact per-backend usage in task telemetry.

06Worked example

“Read this error, fix the code, then test it.”

A concrete sequence shows how the models cooperate without passing a huge transcript around. The figures below are illustrative context sizes, not measurements.

Route the request · about 0.5–1K input

An attachment makes vision relevant. Julia also identifies code/tool needs. The host records the requested scope; no write permission is inferred from a probability score.

Observe the screenshot · one bounded image + task

LFM-VL extracts the error, visible file references and uncertainty. The original screenshot and coordinates remain available. Unclear text is rechecked rather than guessed.

Retrieve the relevant files · about 3–6K input

The context engine looks up matching errors and symbols. K2 reads exact current source, relevant tests and pinned constraints—not the whole repository.

Propose and execute a focused patch

The host checks the expected file revision and workspace boundary. After required approval, it applies the patch and runs a bounded test command in an isolated test environment.

Verify; repair at most twice

Tests, type checks and observed application behaviour determine the outcome. Failed tests return a compact diagnostic packet. A timed-out or truncated model response is not success.

Commit a checkpoint and answer

The controller reports what changed, what passed and what remains unchecked. The compactor records the outcome with source IDs; code and full logs stay retrievable.

No maths expert is needed here. Conversely, a calculation-only task should not load the code or vision model. The quality of routing includes knowing what to leave out.

What we measure

Record time to first visible answer token, total task time, prompt throughput, generated throughput, image time, each model switch, tool time, context tokens, peak VRAM and peak RAM. Separate cold, warm and resumed runs. A progress event is not the first answer token.

How we calibrate

Pin driver, runtime build, checkpoint hash, quantisation, template and sampling. Warm up three times, then run at least 30 repetitions per latency scenario. Use ≥100 runs for more meaningful tail estimates. Report p50/p95 with sample count; throughput alone is insufficient.

08Deployment & resource control

All models on disk. Only useful work on the GPU.

Treat file storage, CPU memory and GPU memory as separate budgets. The package is larger than the active working set.

CPU · normally resident

Decisions and lookup

Julia, SQLite, an embedding worker and the host. Start with a 3–6 GiB planning allowance for these processes; profile actual library and activation overhead. Keep room for Windows, the browser and the filesystem cache.

GPU · scheduled

One active generation

Retain the controller plus at most one specialist only if measured memory fits. Reserve roughly 2 GiB headroom for display/runtime variation. Otherwise unload the controller, run the expert, then reload it.

Disk · persistent

Artifacts and weights

Selected listed weights total about 10.52 GB before embeddings, runtime, browser, indexes and artifacts. Plan 20–30 GB initial free space plus workload storage; installers/updates may need extra temporary space. [S1] [S3] [S5] [S7] [S9] [S11]

09Success criteria

Potential quality markers—not promised scores.

The system earns its complexity only when it outperforms simpler baselines at comparable cost. These are proposed, deliberately testable release targets.

Most promising fit

Bounded local tasks with observable outcomes: code edits with tests, exact calculations, error diagnosis, and document answers with source references.

Needs careful evaluation

Mixed requests, cross-document reasoning, ambiguous screenshots and longer tool sequences. More handoffs can create more failure points.

Do not promise

Frontier-level general reasoning, autonomous high-stakes decisions, exhaustive answers from partial retrieval, or that several small models equal a larger dense model.

A fair comparison

Compare four systems: MiniCPM alone with the same tools; the best practical single larger local model; a single-specialist router; and the complete selective collective. Also ablate retrieval-only versus retrieval + compaction.

Use a 400-task end-to-end holdout split equally across tools, code, maths, vision and mixed tasks. Keep training/tuning data separate. Evaluate raw success, time to verified success, retries and cost; do not report only the easiest category.

Compounding error matters

As an illustration, four independent 95%-reliable stages would yield only about 81% all-stage success. Real failures are not independent, but the calculation shows why excellent-looking per-stage scores are insufficient.

Include wrong-route recovery, original-source re-reading, deterministic checks and abstention. A second model agreeing with the first is not independent proof.

10Trust, permissions & resilience

Bound the autonomy outside the models.

Routing scores can suggest a workflow. They must never grant access to a directory, unlock a browser session or approve a consequential action.

Protect execution

Use an allowlisted tool catalogue and workspace roots, expected-revision patching, explicit shell permission, timeouts, output caps and a dedicated low-privilege account. Require confirmation for deleting outside a sandbox, publishing, sending messages, purchases and privileged installations.

Native processes are not a security sandbox. Untrusted code/tests need a disposable VM or similarly strong isolation. Browser contexts isolate sessions, not the host filesystem. Never execute extracted document instructions as commands.

Recover without repeating harm

Persist the intended action before execution, then its receipt and observed result. Retry read-only calls automatically within limits. For writes, reconcile actual state using an idempotency key or provider receipt; never blindly replay after a crash.

Use loop signatures, a 12-model-step initial cap and at most two repair retries. If the budget is exhausted, save a checkpoint and explain the blocked state. Longer work requires a deliberate budget change.

Keep data correctly scoped

Project permissions apply before retrieval. Store secrets separately, redact them from telemetry, and encrypt sensitive local storage using host facilities. Give users a deletion path covering originals, chunks, vectors, summaries and backup retention.

Version facts and indexes. Changing embedding weights, dimensions or text normalisation triggers a controlled reindex, not mixing incompatible vectors.

Handle bad evidence honestly

Treat web pages, skill imports and tool output as untrusted data. Preserve their origin through compaction. Reject source IDs that do not exist; flag uncertain OCR and conflicting facts. Display offline freshness and incomplete document coverage.

No silent cloud fallback. When a model cannot solve the task within limits, return the evidence and remaining uncertainty or use an explicitly enabled escalation policy.

11Delivery sequence

Build in stages, promote by evidence.

These are implementation milestones and exit conditions, not delivery-time promises. The first useful system should remain small enough to debug.

ACOMPATIBILITY

Pin the environment and prove every selected artifact can run.

DSPECIALISTS

Add vision, maths and code one at a time.

Implement bounded handoffs, role-specific contexts and result schemas. Compare MiniCPM alone with each specialist and the full sequence at matched budgets.

Exit: retain only experts that add measurable task success or latency benefit without unacceptable regressions.
EPACKAGE & LEARN

Create the portable bundle, then investigate training.

Add local setup, health checks, clean shutdown, version rollback and a single API identity. Collect consented, verified task traces. Evaluate router fine-tuning, compatible adapters and distillation as separate experiments.

Exit: clean-machine install and release evaluation pass. Do not claim a single-GGUF model unless a supported integrated architecture is actually produced.
The product is the smallest workflow that reaches a defensible answer.

Not the number of models loaded. Not the advertised context limit. Not the length of the reasoning trace.

Task packet and specialist result schema

A handoff carries an objective, limits and references. The specialist cannot expand its own permissions or declare external work verified without a host receipt.

TaskPacket = {
  task_id, step_id, project_id,
  objective, current_user_request,
  pinned_constraints: [{text, source_id}],
  evidence: [{source_id, revision, range, text, trust_level}],
  allowed_tools: [tool_id],
  budget: {input_tokens, generation_tokens, tool_calls, deadline_ms},
  expected_output_schema
}

SpecialistResult = {
  status: "ok" | "needs_context" | "blocked" | "failed" | "truncated",
  result,
  assumptions: [],
  evidence_refs: [],
  proposed_actions: [],
  unresolved: [],
  verification: {checks_requested: [], host_receipts: []}
}

Store decision summaries, final results and tool receipts. Do not require or depend on private chain-of-thought traces. Never pass raw tokens, KV caches or incompatible embeddings between different models.

Suggested tables: sources, chunks, facts, tasks, steps, tool_calls, approvals, summary_links, embedding_versions. Give facts validity/supersession fields. Deletion cascades and reindex jobs must be explicit and auditable.

Acceptance checklist for a model adapter
  • Loads the pinned file without network access after installation; metadata and hash match the manifest.
  • Uses the correct tokenizer/template and stop rules; handles empty, invalid and over-budget input safely.
  • Parses native tool calls into validated host schemas; handles text-only fallback without regex-based command execution.
  • Respects cancellation and generation limits; distinguishes EOS, error and truncated output.
  • Measures input and generated tokens with the actual model tokenizer; accounts for image tokens and hidden reasoning where present.
  • Correctly loads its projector when needed; maps screenshot coordinates through any resize or crop transform.
  • Reports actual GPU placement, resident memory and timing. Unsupported hardware or CPU fallback is visible to the host and user.
  • Passes a role-specific gold set before its results are trusted in a composite workflow.
